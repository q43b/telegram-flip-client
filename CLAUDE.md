# TG Flip: Android app (read this first)

## What this project is
A personal, study-oriented project: use Telegram on an Android 10 flip phone with a d-pad, in a region where Telegram is blocked. A Python backend (FastAPI + Telethon) runs on the owner's Windows PC in `../server/`. This folder is the native Android app that will talk to it. The repo-level goals, decisions, and milestones are in `../PROJECT_BRIEF.md`.

## Current state
- Backend milestones 1-8 done: chats, messages, send, mark-as-read, live updates, error handling.
- Packaged server: `server/run_server.py` (first-run setup writes `.env`, Telegram login via `client.start()`, then uvicorn from code, all in one event loop) is the entry point of `tgflip-server.exe`. `server/build_server.ps1` builds `dist/tgflip-server-<version>-win64.zip` with PyInstaller (one-folder; `requirements-build.txt`) and refuses to pack `.env`/`*.session`. `.env` and the session live next to the exe. The MTProxy is optional (empty PROXY_HOST = direct). `uvicorn server:app --host 0.0.0.0 --port 9436` still works for development (uvicorn itself defaults to 8000, so pass the port).
- Accounts (since 0.12.0-beta, step 1 of `../docs/multi-account-plan.md`): the server is built around an `Account` object (its TelegramClient, its apps' live connections `ws_clients`, Telegram config, forum unread cache, remembered sticker documents and packs, running video downloads, local favourites file, reconnect lock and watchdog). `ACCOUNTS` holds exactly one today (from .env: API_TOKEN, tg_session, local_favorites.json). The current account travels in a context variable: `current_account` (the router dependency, async on purpose) picks it by the request's token, `ws_token_ok` for live connections, and `@on(...)` handlers (registered per account by `register_handlers` at startup) for Telegram updates; `account()` returns it and `client` is a proxy for its client, so code that talks to Telegram didn't change. Server-wide on purpose: the log, Telegram's standard reactions, custom emoji alts, `seen_apps`, and the media caches on disk (per account in 0.13.0). Several apps on one account work at once (each gets every live event; checked with two connections). For any server change, `server/tools/check_server.py` checks every read-only endpoint and two live connections (statuses and shapes only, no private data); run it before and after and diff. The 0.13.0 handoff (exact names, what to change, test phones) is in `../docs/multi-account-plan.md`.
- Server resilience: the MTProxy sometimes leaves Telethon connected but answering MTPROTO_CLUSTER_INVALID to everything. `connect_telegram()` retries from a clean disconnect at startup; at runtime, endpoints wrapped in `@recovering` reconnect and retry once, and a watchdog checks every 2 minutes.

Release builds (`assembleRelease`) are signed with the owner's key via `android/keystore.properties` (git-ignored; template `keystore.properties.example`); without that file they come out unsigned. Back returns to all chats. Offline, a folder shows those of the saved chats that are in it.
- Older chats: a "Show more chats…" row at the end of the list raises the `/chats` limit by 20 each time (live refreshes keep the bigger limit).
- Forum groups (groups split into topics): marked "›" in the list; OK opens `TopicsActivity.kt`, OK on a topic opens `ChatActivity` for that topic. In the list, F2 on a forum opens its General topic directly (soft key label "Open General").
- A forum group's own unread counter is stale in Telegram (it never clears when topics are read one by one), so `/chats` reports forums as the sum of their topics' unread counts, cached per group until activity there or 60 s.
- Forum caveats to watch: General (topic id 1) is loaded by scanning the group's last 200 messages for ones with no topic mark; topic reads on other devices may not send a live "read" event.

## Target device
- Android 10 flip phone, small screen, d-pad. Keys seen in its browser: ArrowUp/Down/Left/Right, Enter (OK), soft keys F1 (keyCode 112) and F2 (113). Back is handled by the system.
- Known issue in the phone's browser: d-pad Up/Down moves focus two items at once. The reason to build a native app is to handle key events directly (onKeyDown) and fix this.
- 112/113 are the browser's (JavaScript) codes for F1/F2. Native Android numbers keys differently: F1/F2 are `KEYCODE_F1`/`KEYCODE_F2` (131/132), but some phones send soft keys as `KEYCODE_SOFT_LEFT`/`KEYCODE_SOFT_RIGHT` (1/2) and the browser just labels them F1/F2. Accept both pairs.
- Confirmed from the phone's key layout (`/system/usr/keylayout/matrix_keypad.kl`, a Kyocera): OK = `DPAD_CENTER`, soft keys = `F1`/`F2`, plus `BACK`, `CALL`, digits, `STAR`, `POUND`. Helpers live in `SoftKeys.kt`.
- On a screen with a text box, keys go to the keyboard app (IME) first, and the phone's IME swallows OK (F2 gets through; F1 is used by the IME while typing). So the chat screen's message list is `OkListView`, which takes OK in `onKeyPreIme` (runs before the IME). Activity `dispatchKeyEvent` runs after the IME and never sees OK there. The phone is reachable over USB with adb for reading logs. It hides debug log lines (`log.tag=I`), so log with `Log.i`.
- Opening/closing the flip switches the keyboard config; activities declare `configChanges="keyboard|keyboardHidden|navigation"` so screens are not rebuilt.

## Server API (plain HTTP on the home network; the PC has a fixed LAN IP; port 9436, "q43b" in leet; was 8000 until 0.4.0)
- Auth: every HTTP request needs the header `x-token: <API_TOKEN>`. The token is never hardcoded in the repo.
- `GET /chats?limit=20` -> `[{id, name, unread, forum, last}]` (`forum`: group split into topics; `last`: `{text, out, date, sender, kind}` or null, the dialog's newest message, in a forum of any topic; `kind` text/media/event; `sender` only for others' messages in groups; comes with the dialog list, no extra requests)
- `/chats` objects also carry `photo`: the id (a string) of the chat's current profile photo, or null; it changes with the photo.
- `GET /photo/{chat_id}?size=48&photo_id=…` -> a size×size JPEG (16-160; Telegram's small photo is 160), 404 without a photo. Shrunk with Pillow and saved in `photo_cache/` (working folder, git-ignored) as `<chat>_<photo>_<size>.jpg`; with a matching `photo_id` it answers from there without asking Telegram. The first step of the media groundwork: later media should follow the same pattern (id in the list, file from its own request, shrunk and cached on the server).
- `GET /profile/{user_id}` -> `{id, name, username, phone, photo, bot}` for a person (404 for groups, channels and unknown ids). `username`/`phone` null when not set or hidden by privacy; `phone` has its "+". Asks Telegram each time. Its `photo` works with `/photo/{user_id}` (a person's id is also their private chat's id).
- `GET /chats?ids=1,2,3` -> the same objects for exactly those chats (an app folder), newest activity first; built from one GetPeerDialogs request like iter_dialogs builds its own (`dialogs_by_ids`). Chats the account can't resolve are skipped.
- `GET /topics/{chat_id}?limit=50` -> `[{id, title, unread}]` for a forum group; General is id 1
- `GET /messages/{chat_id}?limit=20[&topic_id=N]` -> `[{id, text, out, date, reply_to_id}]`, oldest first (`reply_to_id` null if not a reply)
- `POST /send` with JSON `{chat_id, text, topic_id?, reply_to_id?}` -> `{id}`
- `POST /read/{chat_id}[?topic_id=N]` -> `{ok: true}` (this sends a read receipt, so it must stay a deliberate user action)
- Without `topic_id`, every endpoint works on the whole chat, as before.
- Messages (and live message events) also carry `sender`: the writer's first name (or a channel's title) for other people's messages in groups, null for own messages, private chats and channel posts (`sender_name`; comes with the messages, live events use `event.get_sender()`). The app shows it in bold: "14:05 **Anna:** hi". Next to it, `sender_id`: the writer's user id, set exactly where `sender` is, except for channels posting into a group (`sender_id_of`).
- Messages also carry `edited` (true = show "(edited)"; from Telegram's edit_date, unless edit_hide) and `call` (null, or `{video, reason, duration}` for call records: reason missed/busy/hangup/disconnect/null, duration seconds or null). Calls are service messages; Telethon's NewMessage skips those, so `on_call_record` (events.Raw UpdateNewMessage) broadcasts them live. `/chats` `last` has `kind: "call"` plus `call` for them.
- Messages, live message events and `/chats` `last` carry `voice`: null, or `{duration}` (seconds) for voice messages (`voice_of`); `last` then has `kind: "voice"`. `GET /voice/{chat_id}/{message_id}` -> the OGG/Opus file (`audio/ogg`, about 100-250 KB a minute), 404 if that message is not a voice message; not saved on the server. `POST /send_voice?chat_id=&duration=[&topic_id=][&reply_to_id=]` with the OGG/Opus recording as the raw body (no form parsing, so no python-multipart) -> `{id}`; at most 10 MB; topics and replies as in /send (`reply_target`).
- Messages and live message events carry `image`: null, or `{w, h}` (the photo's full size) for photos (`image_of`; `photo_sizes` lists Telegram's downloadable sizes); `/chats` `last` then has `kind: "photo"` with the caption as `text`. `GET /image/{chat_id}/{message_id}` -> a JPEG shrunk to fit 480×854 (the phone's screen; Pillow `thumbnail`, quality 80, usually 30-60 KB), from the smallest Telegram size that still fills the screen (downloaded by its type letter: Telethon's `thumb=` takes no PhotoSizeProgressive objects); saved in `image_cache/` (git-ignored) as `<chat>_<message>.jpg`, so repeats are instant; 404 if that message is not a photo. `?full=true` instead sends the biggest size Telegram keeps (up to 2560 px), unchanged and not cached (`full_photo`), for saving on the phone.
- Messages and live message events carry `video`: null, or `{duration, w, h, size}` for plain videos (`video_of`: not round videos, GIFs or video stickers, which Telethon also calls videos); `/chats` `last` then has `kind: "video"` with the caption as `text`. `round`: null, or `{duration, size}` for round video messages (`round_of`, Telethon's `video_note`; `last` `kind: "round"`). `GET /video/{chat_id}/{message_id}` (videos and round videos) -> the file unchanged (no converting yet), downloaded once into `video_cache/` (git-ignored, `<chat>_<message>.mp4`, via `cache_path`, the one helper that builds cache paths) and sent from there (`FileResponse`); the answer starts only once the whole video is on the server. Two requests for the same video share one download (`video_downloads`, `asyncio.shield`). 413 over 100 MB (`MAX_VIDEO_BYTES`), 404 if not a video.
- `POST /send_video?chat_id=&duration=&w=&h=[&thumb_size=][&caption=][&topic_id=][&reply_to_id=]` -> `{id}`: the body is `thumb_size` bytes of JPEG preview (≤200 KB, may be 0) followed by the video; written to a temporary folder as it arrives (`request.stream()`, 413 past 100 MB, never held in memory), then `upload_video` (@recovering, so a reconnect retries only the upload, not the already-read body) sends it with `DocumentAttributeVideo(duration, w, h, supports_streaming)` and the preview.
- `POST /send_photo?chat_id=[&caption=][&topic_id=][&reply_to_id=]` with the picture as the raw body (`Content-Type` image/jpeg, image/png or image/webp picks the file name Telethon sees) -> `{id}`; at most 10 MB; sent as a photo (`force_document=False`), so Telegram makes its own sizes; topics and replies as in /send.
- Messages, live message events and `edited` events carry `reactions`: `[{emoji, count, mine}]` in Telegram's order (`reactions_list`/`reactions_of`; `mine` = `chosen_order` set; `custom_id` for custom emoji; custom emoji → their plain "alt" emoji, learned once per id with `GetCustomEmojiDocumentsRequest` and kept in `custom_emoji_alts` (`learn_custom_emoji`, called before building lists: all at once in /messages, per live event via `learn_live_custom_emoji`), "✦" if unknown; paid → "⭐"; plain entries are Telegram's own, custom ones each their own entry). Reaction changes come as `events.Raw(UpdateMessageReactions)` → `{type: "reactions", chat_id, id, reactions}`.
- Messages and live message events carry `sticker`: null, or `{id, emoji, kind}` (kind static/animated/video by mime type; `sticker_of`, which also remembers the document in `sticker_documents`, since downloading needs it); `/chats` `last` `kind: "sticker"` with the emoji as `text`. `GET /sticker/{id}?size=128[&chat_id=&message_id=]` -> a still PNG at most size×size (32-512), transparency kept: a static sticker's own WebP, or for animated/video ones Telegram's still preview (`thumb=-1`); cached in `sticker_cache/<id>_still_<size>.png` (git-ignored, `cache_path`). The document comes from `sticker_documents`, else (after a restart, or an expired file reference) from reading the message again; 404 when unknown or without a picture.
- Messages, live message events and `edited` events carry `custom_emoji`: `[{offset, length, id}]` from MessageEntityCustomEmoji (`custom_emoji_of`; UTF-16 units, as Kotlin strings index). Since 0.10.1-beta `/messages` sends `raw_text` (plain, like live events; before, Telethon's markdown `m.text` added `**`/`[]()` marks that broke these offsets). Reactions carry `custom_id` (null for plain ones); custom emoji entries are no longer added up on the server. `/sticker/{id}` without chat_id/message_id takes the id as a custom emoji's and asks `GetCustomEmojiDocumentsRequest` for it (documents learned for reactions are remembered too); a fully transparent still (outline-only custom emoji) answers 404.
- `GET /sticker_sets` -> `{packs: [{id, title, count}]}` my installed packs (GetAllStickers; their access hashes kept in `sticker_sets`). `GET /sticker_set/{pack}` -> `{stickers: [{id, emoji, kind}]}` for "recent" (GetRecentStickers), "faved" (GetFavedStickers) or a pack id (GetStickerSet); each is remembered (`sticker_json`) for /sticker and sending. `GET /sticker_set_of/{sticker_id}[?chat_id=&message_id=]` -> `{pack: {id, title, count, installed}, stickers}` (the pack in the sticker document's DocumentAttributeSticker; 404 for stickers in no pack; installed = installed and not archived). `POST /sticker/{id}/fave[?unfave=true]` -> `{ok}` (FaveStickerRequest; refusals logged with Telegram's reason). `GET /sticker_set/local` -> the local favourites; `POST /sticker/{id}/local_favorite[?remove=true]` -> `{ok}`: kept in `local_favorites.json` next to .env (git-ignored, refused by build_server.ps1 like secrets), newest first, as `{id, set_id, set_hash}` so the server can reload each sticker from its pack (GetStickerSet once per pack when listing; stickers from deleted packs drop out; stickers in no pack can't be kept, 400). Per account later. `POST /sticker_set/{id}/install` -> `{ok}` (InstallStickerSetRequest; packs the server has seen). `POST /send_sticker` `{chat_id, sticker_id, topic_id?, reply_to_id?}` -> `{id, sticker}`, for stickers the server has seen (404 otherwise: open the pack again).
- `GET /reactions/{chat_id}` -> `{reactions: [emoji]}`: the plain emoji reactions I may choose there, my most used first (`GetTopReactionsRequest`, best effort), then the rest in Telegram's order (`GetAvailableReactionsRequest`, active ones, asked once). Private chats allow all, except Saved Messages without Premium (none: Telegram uses reactions there as Premium "tags", and refuses them otherwise); groups/channels by their `available_reactions` (All / Some / None → []). `POST /react` `{chat_id, message_id, emoji}` (emoji null or "" = take mine back) -> `{reactions}` as they are now: from Telegram's answer (an `UpdateMessageReactions`, or the edited message in `UpdateEditMessage`/`UpdateEditChannelMessage`), else by reading the message (Telegram sends no live update for my own reaction, so the app redraws from this answer); sends `SendReactionRequest` with `[ReactionEmoji]` or `[]`.
- `POST /edit` `{chat_id, message_id, text}` -> `{ok}` (400 when too old: Telegram's edit_time_limit)
- `GET /delete_options/{chat_id}/{message_id}` -> `{for_me, for_everyone}`, worked out from chat type, message age and owner, admin rights, and Telegram's config (revoke_pm_time_limit, revoke_pm_inbox, revoke_time_limit). Supergroups/channels have no "for me".
- `POST /delete` `{chat_id, message_id, revoke}` -> `{ok}` (`revoke` = for everyone)
- `POST /forward` `{from_chat_id, message_id, to_chat_id}` -> `{id}` (into a forum: lands in General)
- `WebSocket /logs`: the server's console log for the app. Token first (`ws_token_ok`, shared with /ws), then one JSON list of the kept lines (`log_lines`, last 500, each "HH:MM:SS text", colors stripped), then a list of one per new line. Captured by `LogTee` (replaces sys.stdout/stderr at import) and, under `uvicorn server:app` (which sets up its logging with the real console before importing server.py), a `LogRecorder` handler on the uvicorn loggers (`start_log_capture` at startup picks one, so no line doubles; uvicorn's first two startup lines come before it and are missed there). Sending lines logs nothing, so watching can't feed itself; only opening/closing the connection is logged.
- `WebSocket /ws`: the first text message must be the token (the server closes the connection after 5 seconds without it). The server then pushes JSON:
  - `{type: "message", id, chat_id, topic_id, reply_to_id, text, out, date}` (`topic_id` is null in ordinary chats and in General)
  - `{type: "read", chat_id}` (read state changed in another client; refetch `/chats`)
  - `{type: "edited", id, chat_id, text, edited}`
  - `{type: "deleted", chat_id, ids}` (`chat_id` is null outside channels/supergroups; there ids are unique per account)
  - `{type: "call_ringing", call_id, chat_id, name, video}` (someone is calling now; from UpdatePhoneCall/PhoneCallRequested) and `{type: "call_ended", call_id}` (it stopped ringing: accepted, answered elsewhere or discarded). The app's `IncomingCallAlert` shows a dialog (no vibration: the owner doesn't want it) on the open screen (not Settings, which has no live connection) and closes it on call_ended. Only while the app is open.
- After a WebSocket reconnect, refetch current state (chats and the open chat's messages).

The full plan is in `../docs/multi-account-plan.md`; the owner wants it after video, stickers and reactions. Until then, write new server features so the Telegram client and cache paths come from one place each (easy to make per-account later).
- The app and server share only a base URL and a token. How the phone reaches the server is a separate, swappable layer. Keep the protocol plain HTTP + WebSocket.
- The home ISP uses CGNAT and the PC has no real public IPv6 (only Teredo), so there is no direct remote access. Remote access is shelved (2026-11-05), all options ruled out:
  - Tailscale/TailSocks: the provider's DPI disrupts it; the PC only gets through thanks to Zapret, the phone never went online (TailSocks's built-in DPI bypass did not help), and an earlier try failed on mobile data.
  - No public IPv4 from the ISP; Cloudflare is blocked; a foreign VPS risks its IP being blocked; Russian VPSs may not be used for bypassing by law.
  - The connection modes (VPN, Public) stay in the app for later.
- Android 17+ (API 37, the app's target): reaching home-network addresses needs the runtime permission `ACCESS_LOCAL_NETWORK` (shown as "Nearby devices"); without it every request fails silently ("Can't reach server"). Found on a Pixel 8 Pro with Android 17 (0.12.1-beta). `LocalNetworkAccess.missing` (Android 17+, Local/VPN modes, not granted); the chat list asks once per screen before connecting (`askLocalNetwork`), connects when allowed, otherwise says where to allow it. Older phones (the Kyocera on 10) never see it.
- Plain HTTP: `network_security_config.xml` allows it in general (it is fixed at build time and cannot follow Settings). The app limits it itself: it only connects to the addresses entered in Settings; Local network and VPN modes use http, Public internet always https (`ConnectionMode.scheme`).
- Message text must never be rendered as HTML.
- Keep the app light: it runs on a weak phone.
